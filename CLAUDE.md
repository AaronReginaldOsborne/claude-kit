# claude-kit: working rules for this repo

This repo packages Aaron's Claude Code setup for a friend who runs a business and already uses Claude Code. The friend is not part of Aaron's companies, and their OS is unknown (macOS, Windows or Linux). The friend's Claude Code clones this repo into their home folder, reads `SETUP.md`, and installs what `kit.json` lists, **globally (user scope), so it works in every project on their machine** (Aaron's requirement). This file is for whoever maintains the kit (Aaron, or Claude working for him).

**If you are the friend's Claude running SETUP.md, this file is not for you: follow SETUP.md and do not edit anything in this folder.**

## What is actually here (verified 2026-09-27)
- `kit.json`: the single source of truth: groups (with the items asked about separately), marketplaces, plugins, skills, GSD, CLI tools, MCP templates with placeholders and pinned versions, key entry, uninstall commands, the install record, undo, verification, `open`, `notIncluded`.
- `SETUP.md`: the procedure the friend's Claude follows (rules, Steps 0 to 6, re-run, Undo, troubleshooting). It holds no item list of its own.
- `README.md`: for Aaron and the friend (before you paste, paste prompt, what it installs, where the kit lives, updating, undo, adding items, not included, OPEN).
- `.claude-plugin/marketplace.json` + `plugins/aaron-kit/`: this repo is the `aaron-kit` marketplace with one plugin (v1.0.0) holding three skills, byte-for-byte copies of Aaron's `first-website`, `production-readiness` and `seo-strategy` (each is a single `SKILL.md`). The friend's Claude Code loads the plugin from the clone, so the clone must stay in place.
- `files/`: byte-for-byte copies of Aaron's global rules (`CLAUDE.md`) and the `/antivibe-docs` command, plus the Windows launcher for the nano-banana-pro MCP server (`launcher.mjs`, `package.json` with exact versions, `package-lock.json`). The launcher has the same logic as the one Aaron runs; its comments were rewritten and one log message was capitalised.
- `tools/kit-files.mjs`: a standard-library Node helper that adds, updates and removes the kit's marked rules block in the friend's `CLAUDE.md`, compares files, snapshots the working folders before an install and re-checks them after (Step 1b and Step 5), and prints JSON key names without values. `tools/kit-files.test.mjs` tests it (`node --test tools/kit-files.test.mjs`).
- `CLAUDE.md` (this file) and `docs/`: for maintaining the kit. SETUP never installs them.
- No build step and no dependencies at the repo root. Install commands are verified by hand and recorded in `kit.json`.
- Git: branch `main`. The kit lives in a public GitHub repo, `https://github.com/AaronReginaldOsborne/claude-kit` (Aaron's decision, 2026-09-27, `docs/DECISIONS.md`; published 2026-09-27). Anyone can clone it over HTTPS without a GitHub account or sign-in. Commits use Aaron's GitHub noreply address (the repo's `user.email`).

## Tooling it was verified with
Windows 11 (Git Bash and PowerShell 5.1), Claude Code 2.1.257, Node 22.14 (the skills CLI wants 22.20+ and only warns below it), `npx -y skills@1.7.0`, `npx -y get-shit-done-cc@1.42.3`, uv 0.10.7, git. ## Rules
1. **`kit.json` is the source of truth.** Items, commands, flags, pins and placeholders live there only. README tables and SETUP wording follow it; change `kit.json` first.
2. **Global scope only.** Every install command carries its scope flag explicitly: `--scope user` (marketplaces, plugins, MCP servers), `-g ... --copy` (skills CLI), `--global` (GSD), `npm install -g` (CLI tools). Never add a project- or local-scope step. `claude mcp add` defaults to local scope, so the flag is not optional. Every item also has an `uninstall` command with the same scope.
3. **Never commit secrets.** No keys, tokens, `.claude.json`, credential or token files. MCP entries use placeholders such as `<YOUR_GEMINI_API_KEY>`; the friend's keys never enter this folder or any file SETUP writes.
4. **Never commit Aaron's personal or company items.** No history, memory, projects, permissions or local paths, and nothing from Aaron's businesses or partners (company skills and commands, the ghl, liquid-sunset, quickbooks and gimp MCP servers). Name those items only in the `notIncluded` lists and the maintainer docs (`CLAUDE.md`, `docs/`), and do not name the companies themselves in prose. The auto-allow permission hook stays out. New exclusions go in `notIncluded` and the README table.
5. **Third-party skills and plugins are installed from their source, never copied in.** Only Aaron's own skills, rules and command are copied, and copies stay verbatim: re-copy from the original and compare hashes instead of editing them here.
6. **Pin what holds a key.** Every MCP package that runs with the friend's key is pinned to an exact version (npm `@x.y.z`, uvx `@x.y.z`, the launcher's exact `package.json` plus lockfile). Aaron bumps pins deliberately, after testing the new version.
7. **Test every install command in a sandbox home before listing it.** Read its `--help`, dry-run with `--list` where the tool has one, then install with `HOME`, `USERPROFILE`, `CLAUDE_CONFIG_DIR` and `npm_config_prefix` pointed into an empty folder (and npm's bin folder for that prefix, the prefix itself on Windows and `<prefix>/bin` on macOS/Linux, put first on `PATH`), from an empty working directory. Confirm it landed at user scope in the sandbox and that the working directory is still empty. Known leaks: on Windows, native binaries such as agent-browser find the home folder through the system and ignore `HOME`/`USERPROFILE`, so never run `agent-browser install` in a test; the GSD installer links `gsd-sdk` into `npm prefix -g` on Windows (which follows `npm_config_prefix`) and into a folder under `HOME` on macOS/Linux, and skips the link when a `gsd-sdk` is already on `PATH`. An earlier run without `npm_config_prefix` re-linked the maintainer's own `gsd-sdk` on 2026-09-27. Never run the PATH-change lines GSD prints during a test: on Windows its PowerShell line permanently changes the real user PATH. With claude-mem installed in a sandbox, `claude mcp list` and `claude mcp get` health-check its server, which connects to the claude-mem worker on 127.0.0.1 at its default port (37777 on Windows; claude-mem 13.0.0 computes the default from the user id on macOS/Linux), which is the maintainer's REAL worker when one is running: before any `mcp list/get`, disable it inside the sandbox (`claude plugin disable claude-mem@thedotmack --scope user`) or set `CLAUDE_MEM_WORKER_PORT` to a free port in `<sandbox>/.claude-mem/settings.json` (claude-mem reads it from `<home>/.claude-mem/settings.json`, read in its `mcp-server.cjs`). Run sandbox checks while no other Claude session is starting: a starting session's marketplace auto-refresh updates `lastUpdated` in the real `~/.claude/plugins/known_marketplaces.json`, which can be mistaken for a sandbox leak. Anything not verified goes under `open`.
8. **Plugin updates need a version bump** in `plugins/aaron-kit/.claude-plugin/plugin.json`; without one, `claude plugin update` reports "already at the latest version".
9. **Docs are the record.** A decision or tradeoff goes into `docs/DECISIONS.md` and the affected doc in the same change. Unknowns are marked OPEN, never guessed.
10. **The repo is public: everything committed is world-readable**, history included, so rules 3 and 4 are absolute. No secret and no personal or company item goes into any commit, not even briefly: deleting it in a later commit does not unpublish it. Commit with the GitHub noreply address, never a personal email.

## Definition of Done for a change
- `node -e "require('./kit.json')"` parses; `claude plugin validate .` and `claude plugin validate ./plugins/aaron-kit --strict` pass; `node --test tools/kit-files.test.mjs` passes.
- Every new or changed command verified in a sandbox home as in rule 7, and how it was checked (and on which OS) noted in `kit.json` (`verified` or `note`), or the gap listed under `open`.
- Copied files match their originals by sha256 (only when a copy was refreshed).
- No secret or personal/company item in the change (the KIT-010 searches in `docs/FEATURE_TICKETS.md` still find nothing).
- README, SETUP and `kit.json` agree on names, groups, commands, pins and OPEN items.
- `docs/DECISIONS.md` and the affected doc updated in the same change.
- Nothing committed or pushed without Aaron's go-ahead (a push publishes to the world, rule 10).
