# Architecture

## Pieces
- **Paste prompt (README)**: the friend's Claude Code, started in the home folder, clones the repo to `~/claude-kit` (or pulls it when already there; the repo is public, so no sign-in is needed; it stops and says what to install if git is missing, and stops and shows the error in plain words if the clone fails) and follows SETUP.md, installing everything at user scope. A second prompt runs SETUP's Undo.
- **SETUP.md**: the procedure (rules, Steps 0 to 6, re-run, Undo, troubleshooting). It holds no item list of its own; it reads `kit.json`.
- **kit.json**: every item, command, uninstall command, pin, flag, placeholder, disclosure question and verification rule.
- **File helper**: `tools/kit-files.mjs` (standard-library Node, tested by `tools/kit-files.test.mjs`) reports the state of the rules block in the user `CLAUDE.md`, adds it, updates it after a yes and removes it for Undo; it also compares files byte for byte, snapshots the working folders before an install and re-checks them after (`snapshot`, `compare`), and prints JSON key names without values (`keys`). SETUP uses it instead of Claude's read and write tools, so file contents and settings values never pass through the chat, and it behaves the same in bash, zsh and PowerShell on every OS.
- **Local marketplace**: `.claude-plugin/marketplace.json` declares the plugin `aaron-kit` at `./plugins/aaron-kit`. It is added by absolute path (`claude plugin marketplace add "<KIT_DIR_ABSOLUTE>" --scope user`), so once the repo is cloned the plugin needs no further GitHub access, but it keeps loading from that folder: moving or deleting `~/claude-kit` breaks it (verified; recovery commands in `kit.json`). An update reaches the friend through `git pull`, then `claude plugin marketplace update` and `claude plugin update`, and only when the plugin `version` was raised.
- **Copied files**: `files/CLAUDE.md` (added as a marked block to the user `CLAUDE.md`) and `files/commands/antivibe-docs.md` (copied to the user `commands/`). The command stays outside the plugin so its name stays `/antivibe-docs`, the name the rules use.
- **Windows launcher**: `files/mcp/nano-banana-pro/` (launcher, exact-version `package.json`, `package-lock.json`) is copied to `<USER_CLAUDE_DIR>/mcp/nano-banana-pro/`, installed there with `npm ci --prefix` and registered with `node .../launcher.mjs`. macOS and Linux use the plain pinned `npx` command.
- **Install record**: `<USER_CLAUDE_DIR>/claude-kit-record.json` on the friend's machine lists what the kit installed and what it found already there, so re-runs and Undo touch only the kit's own items.
- **Maintainer docs**: root `CLAUDE.md` and `docs/`. Not installed on the friend's machine.

## Hard constraints
- User scope only, explicit flags (the two commands with no scope option, `claude plugin marketplace update` and `agent-browser install`, are named in `scopeRule.noScopeOption`), run from the home folder, and a final check against a snapshot taken right after the prerequisite check (Step 1b) that nothing appeared or changed in the home folder or the session folder: the fixed list (`.mcp.json`, `skills-lock.json`, `.agents/skills/`, a `CLAUDE.md` in the folder itself, `.claude/settings.local.json`) in both, plus every path under each `.claude/` that is not `USER_CLAUDE_DIR` (the session folder's when it is not the home folder; the home folder's when `CLAUDE_CONFIG_DIR` points elsewhere), because project-scope plugins and marketplaces write its `settings.json` and a non-global GSD writes a whole `.claude/` (a `settings.local.json` change only under `permissions` is the human's approvals, not an install, and a new folder is flagged only when it is empty or something inside it is). Marketplace scope is proven by key names in the user `settings.json` / `plugins/known_marketplaces.json`, since `claude plugin marketplace list --json` shows no scope; a kit marketplace in a watched project settings file counts only when `compare` reports it new since the snapshot (`marketplacesAdded`).
- `USER_CLAUDE_DIR` is `CLAUDE_CONFIG_DIR` when set, else `~/.claude`. With `CLAUDE_CONFIG_DIR` set, `claude mcp add --scope user` writes `.claude.json` inside that folder, and the skills CLI's `-g` and GSD's `--global` install into it (all verified 2026-09-27).
- Marketplace sources must be HTTPS: the `owner/repo` shorthand clones over SSH and fails without SSH keys (verified).
- The skills CLI overwrites a same-name folder without asking (verified), hence the ownership check and the edit check in SETUP 4d.
- `claude mcp get` prints key values (verified), hence the filtered output in SETUP. A local-scope MCP entry wins over a user-scope one of the same name (verified), hence the scope check in SETUP 4g.
- Windows: `@rafarafarafa/nano-banana-pro-mcp` does not start through npx (verified), hence the launcher. Very long clone paths can hit "Filename too long" (seen only with a very long temp path; SETUP has the fix, asked first). Windows PowerShell 5.1 has no `&&`, so multi-step commands are lists in `kit.json`.
- Node 22.20 or newer (skills CLI engines), 24 LTS recommended (agent-browser 0.27.1+); Bun for claude-mem; uv for meta-ads. On macOS and Linux a root-owned npm global folder makes `npm install -g` fail with EACCES; SETUP fixes it only on the human's yes.
- Some user-level writes land outside the user Claude folder, and that is expected: the user `.claude.json`, the skills CLI's `~/.agents/.skill-lock.json`, the `gsd-sdk` command (npm's global folder on Windows; a PATH folder in the home folder or `~/.local/bin` on macOS/Linux; it points into npm's npx cache, so deleting `<npm cache>/_npx` breaks it, and GSD's uninstall leaves it, so Undo deletes it only on a yes), agent-browser in npm's global folder and its Chrome in `~/.agent-browser/`, claude-mem's `~/.claude-mem/` (and uv, which it installs when missing), the npm, uv and Bun caches, and, only after the human's yes, `~/.npmrc` with `~/.npm-global/` (the EACCES fix) and a PATH line in the shell profile (EACCES fix or `gsd-sdk`), recorded as `npm-prefix` / `gsd-sdk-path`. The list is `kit.json` → `scopeRule.expectedUserLevelWrites`.
